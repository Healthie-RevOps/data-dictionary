## Why this can't be worked around in-session

The Cowork shell sandbox is reset between sessions, so installing the Salesforce CLI here on the fly would not persist to the next scheduled run, and would still need a one-time interactive `sf org login web` step to authenticate against the production Salesforce org. Both of those need to happen in the user's normal environment (or in a persistent runner), not inside this scheduled task.

## What the user needs to do to unblock the next run

1. Install the Salesforce CLI on the machine that hosts this scheduled task. Official guide: https://developer.salesforce.com/tools/salesforcecli
   - macOS: `brew install salesforcecli/homebrew-sf/sf`
   - npm (any OS): `npm install -g @salesforce/cli`
2. Authenticate against the production org and mark it as default:
   ```
   sf org login web --set-default --alias prod
   ```
3. Confirm it sticks: `sf org list --json` should show the org with `"isDefaultUsername": true`.
4. Re-run this scheduled task (or wait for the next weekly cadence).

Once `sf` is on `PATH` and a default org is authenticated, the rest of the workflow — schema pull, dictionary diff, rolling 6-month "New" flag refresh, and HubSpot page update — should run end-to-end without further intervention.

## Follow-up applied 2026-05-18 (post-abort)

The scheduled task's prompt was rewritten so the next run will not hit the same blocker:

- **CLI bootstrap built into the task.** The new prompt installs `@salesforce/cli` to `$HOME/.npm-global/bin` on every run if `sf` is not already on `PATH`, then exports the path. Verified in the sandbox: `sf --version` now returns `@salesforce/cli/2.134.6`.
- **Non-interactive auth.** The task no longer calls `sf org login web` (impossible inside a scheduled run — no browser). Instead it reads an SFDX auth URL from `Data Dictionary/.sf-auth/auth-url.txt` and runs `sf org login sfdx-url --sfdx-url-file ... --set-default --alias prod`.
- **Stale paths fixed.** All `/sessions/youthful-vigilant-rubin/...` references in the prompt were replaced with a `$WORKSPACE` value resolved at runtime from `/sessions/*/mnt/Data Dictionary`, which is stable across Cowork session names.
- **Workspace scaffolding created.** `Data Dictionary/.sf-auth/README.md` documents the one-time setup; `auth-url.txt.example` is a template.

**One thing the user still needs to do** before next Monday's run: on the local machine, run `sf org display --target-org prod --verbose --json`, copy the `sfdxAuthUrl` value, and save it to `Data Dictionary/.sf-auth/auth-url.txt`. Full instructions in the README.

Dry-run on 2026-05-18 confirmed each step short of the actual login (which can't run until the auth URL is supplied).

## 2026-05-19 update — second, deeper blocker found

Bill supplied a valid SFDX auth URL (`Data Dictionary/.sf-auth/auth-url.txt`, instance `healthie.my.salesforce.com`). The login itself was attempted and failed with:

> `RefreshTokenAuthError: Error authenticating with the refresh token due to: Connection blocked by network allowlist` (HTTP 403 from Salesforce OAuth)
