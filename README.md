## What you get

Two generator scripts and the artifacts they produce:

- **[generate_sfdc_dictionary_html.py](generate_sfdc_dictionary_html.py)** — primary script. Builds the live SFDC web dictionary, pushes it to HubSpot.
  - Output: [peapod_sfdc_data_dictionary.html](peapod_sfdc_data_dictionary.html) (body fragment), [peapod_sfdc_data_dictionary_standalone.html](peapod_sfdc_data_dictionary_standalone.html) (with `<html>`/`<head>` for local preview), [deploy_template_peapod_sfdc_data_dictionary.html](deploy_template_peapod_sfdc_data_dictionary.html) (full HubSpot template).
- **[generate_hubspot_dictionary.py](generate_hubspot_dictionary.py)** — earlier script that produces a .docx mirror of the HubSpot side via the HubSpot CRM properties API.
  - Output: [Healthie_HubSpot_Data_Dictionary_v2.docx](Healthie_HubSpot_Data_Dictionary_v2.docx).

## SFDC dictionary feature set

The published SFDC page surfaces V5 docx content augmented with live Salesforce metadata pulled at run time. All Salesforce data uses the `sf` CLI under the hood, so the CLI must be authenticated to `bill.coffin@gethealthie.com` (or whichever target org is set as default).

| Feature | Source |
| --- | --- |
| Field labels | `FieldDefinition.Label` (authoritative; overrides V5 labels) |
| API names | `FieldDefinition.QualifiedApiName` |
| Setup-page deep links per field | `FieldDefinition.DurableId` (handles custom-field 15-char IDs and standard relationship names) |
| Data types | `FieldDefinition.DataType` |
| Field descriptions | `FieldDefinition.Description` (falls back to V5 when SFDC's is empty) |
| Fill % (color-coded chips) | `SELECT COUNT(<field>) FROM <object>` aggregates, divided by total record count |
| Picklist active values | `sf sobject describe` per object, filtered to `active: true` |
| ★ Key fields (yellow rows) | Heuristic on `FieldDefinition.DataType` (Lookup/MasterDetail/Hierarchy/RecordType) + `_ID__c` external-ID suffix |
| **NEW** green chips | `CustomField.CreatedDate` within rolling 180-day window |
| ⚠ Similar field tooltips | Per-object token clustering on field labels (shared distinctive tokens like "Vitally", "Stripe", "Healthie") |
| Per-object color accents | Hardcoded palette (`OBJECT_COLOR` constant) — Account indigo, Contact cyan, Opportunity amber, etc. |
| SFDC Flows section | `Flow` (Tooling API) joined to `FlowDefinition` for developer names. Includes inferred triggering object from name prefix. |
| Sensitivity pills (PII / Financial / Internal) | V5 docx |
| Source / Update, Owner | V5 docx |
| Dependencies / Notes | V5 docx |

## Regenerating

```bash
# Full run — fetches everything from Salesforce, renders HTML, pushes to HubSpot
python3 generate_sfdc_dictionary_html.py
```

Flags:

- `--render-only` — skip Salesforce calls, use cached metadata, just re-render the HTML.
- `--skip-sfdc` — like `--render-only` but doesn't touch caches at all.
- `--refresh` — invalidate all caches and re-fetch everything.
- `--refresh-fielddefs` — re-fetch just the `FieldDefinition` cache for all objects.
- `--refresh-fill` — re-fetch just the Fill % counts.
- `--refresh-picklists` — re-fetch just the picklist values via `sf sobject describe`.

Caches live under [`.dictionary_cache/`](.dictionary_cache/) keyed by data source (`sfdc_fielddef_*.json`, `sfdc_fill_*.json`, `sfdc_picklist_*.json`, `sfdc_total_*.json`, `sfdc_flows.json`, `sfdc_custom_field_dates.json`). They make iterating on the renderer cheap; live SFDC calls only run when you ask for them or there's nothing cached yet.

## Publishing to HubSpot

The generator pushes the wrapped template to HubSpot's source-code API automatically (`cms.source_code.write` scope required, currently granted on the personal access key in [hubspot.config.yml](hubspot.config.yml)).

One manual step is still needed after the push: click **Update** on the landing page in HubSpot's UI to refresh the prerender cache. Details in [UPLOAD_TO_HUBSPOT.md](UPLOAD_TO_HUBSPOT.md).

## Source documents

- **[Healthie_SFDC_Data_Dictionary_v5.docx](Healthie_SFDC_Data_Dictionary_v5.docx)** — canonical V5 dictionary (469 fields across 7 objects). The parser walks every 8-column field table, plus front-matter and appendix tables. SFDC label drift is corrected at render time by preferring `FieldDefinition.Label`; the docx itself is also kept in sync via in-place renames where appropriate.
- **[Data_Dictionary_Proposed_Fills.md](Data_Dictionary_Proposed_Fills.md)** — earlier heuristic-fills doc, kept for reference. Not used at render time.
- **[hubspot.config.yml](hubspot.config.yml)** — HubSpot CLI config + personal access key. The script reads the access token directly from this file. Refresh on demand with `hs accounts info`.

## Dependencies

- Python 3.9+ (stdlib only — no `requests`, no `PyYAML`)
- `sf` CLI (Salesforce CLI v2.x), authenticated to the target org
- `hs` CLI (HubSpot CLI) for token refresh

## Known caveats

- **TaskRay Project**: `sf data query --use-tooling-api` returns FieldDefinition fine, but `SELECT COUNT() FROM taskray__Project__c` returns "sObject type 'taskray__Project__c' is not supported" — a user-permission gap on the managed package, not a script issue. TaskRay fields render with `—` for Fill %.
- **One unmatched V5 label**: Opportunity → "Using Mobile White Label" doesn't resolve to a current SFDC FieldDefinition. Rendered with plain text (no link). Likely a renamed or deleted field that V5 hasn't reflected yet.
- **HubSpot prerender cache**: after API push, live page serves the previous prerendered HTML for up to 10 hours until the page is "Updated" in HubSpot's UI. See [UPLOAD_TO_HUBSPOT.md](UPLOAD_TO_HUBSPOT.md).
